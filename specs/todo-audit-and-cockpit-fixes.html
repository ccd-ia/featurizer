Purpose

Six open TODO.org entries were checked against the code this session. Three describe real, unfixed defects; three describe work that landed months ago and was never closed. This plan fixes the first group through the protected-master flow, closes the second group with the evidence that settles it, and then extends the same verification to the remaining twenty open entries — because if six entries produced three false claims, the rest have not earned their credibility either.

Problem

A task list that asserts things the code contradicts is worse than an empty one: every entry gets re-read, re-investigated, and re-costed by whoever opens the file next. Three of the six entries examined were stale — group_000 was guarded and tested in c2c8aba, ADR-0010's real-database target was met and recorded in ADR-0012/0013, and CLAUDE.md was rewritten on 2026-09-05 — and a fourth, the branch-protection entry, still says "master has NO protection", which stopped being true on 2026-09-06. Meanwhile two genuine defects sat behind that noise, and one entry proposed a fix ("a settle on the query worker group") that has existed in lynkeus/src/lynkeus/testing.py since its first commit.

Solution

Four phases, ordered so the cheapest and least reversible work happens first. Phase 1 is desk work on two gitignored files and needs no pull request. Phase 2 extends the same evidence standard to the other twenty entries. Phases 3 and 4 are one pull request each, through the protected-master flow: an issue first, a worktree branch off origin/master, eight green contexts, the worktree removed before the rebase merge, and Closes #N in both the commit message and the pull-request body so the issue closes itself on merge.

The merge sequence, in the order that works

Removing the worktree before merging is not a style preference. gh pr merge --delete-branch ends with three local git steps, and a live worktree breaks two of them — verified the hard way on PRs #1, #3 and #5. In every failure case the pull request is already merged, so the repair is git branch -D plus git push origin --delete, never a second merge.

git worktree add .worktrees/<need> -b <who>/<need> origin/master
# ... work, commit with "Closes #N" ...
gh pr create                      # "Closes #N" in the body too
git rebase origin/master
git push --force-with-lease
gh pr checks --watch --fail-fast  # eight contexts, strict
git worktree remove .worktrees/<need>    # from the MAIN checkout, first
gh pr merge <n> --rebase --delete-branch
git branch -vv                    # gh has skipped this step silently before

Why Closes #N goes in both places

GitHub closes a referenced issue from the pull-request body on merge, and from any commit message that lands on the default branch. This repo requires linear history and merges with --rebase, so the commits do land on master and either location would work on its own. Putting the keyword in both costs nothing and survives a squash, a hand-edited body, or a merge performed from the web UI by someone else. The final validation step still checks gh issue list, because a keyword that silently fails to fire looks exactly like one that was never written.

The eight required contexts

Both pull requests wait on the same set, and strict: true means a branch that has fallen behind master will not merge until it is rebased:

fast tests (py 3.10)   fast tests (py 3.11)
fast tests (py 3.12)   fast tests (py 3.13)
integration (PostgreSQL 14)   integration (PostgreSQL 16)
integration (PostgreSQL 17)   packaging (build + twine check)

The gauge change is covered only by the three integration contexts — the fast tier cannot reach it, because status() opens a connection. That is why just db-up is the first validation step in Phase 3: without a database the integration tier skips, and a skip reads like a pass.

  • A global svg { display: block } reset breaks inline MathJax flow on this site — a documented, hard-won gotcha. Phase 4 adds SVGs to one page; if it tempts anyone toward a global SVG rule, that is the trap.
  • No new dependency in either phase. Nothing to uv add, nothing to npm install, no lockfile churn — which also keeps both pull requests off rule 2's all-consumer list.
