Purpose

Close every open GitHub issue. All six were verified against the code before this plan was written — each line reference still resolves, and no commit has touched featurizer/ since they were filed. They are not six independent complaints: three are one validation defect, one is a quoting inconsistency, one is a config block read on only half the paths, and one is a cohort shape the engine cannot express.

Problem

Two of the six could not have been found by testing harder. Every performance number this project has published — ADR-0009, ADR-0010, ADR-0012, ADR-0013 and the v1.0.0 live revalidation — was measured with exactly one as-of date: benchmarks/final_matrix.py:174-180 inserts a single row, bench.py:66 hardcodes one, _db.py:87 passes one tuple, and the published artifacts carry the key as_of_date, singular. At one date the dense cross product is the answer, so the waste ratio is 1:1 and #10's pathology is structurally invisible. The correctness tier does use two or three dates, at row counts where a 3:1 product is a few thousand rows.

#11 is the mirror image: the heap-row ceiling was found, during v1.0 hardening, and guarded — HEAP_ROW_BUDGET_BYTES landed in c2c8aba and the estimator is accurate to within 2% of the reporter's measurement. But it guards only the table featurizer writes. A consumer materializing the same matrix with their own COPY gets no pre-flight, and the configuration reference still names only column counts.

Solution

Five pull requests, ordered cheapest-and-most-blocking first. Each opens against its existing issue, branches in a worktree off origin/master, carries the test that fails without it, waits on eight green contexts, and closes its issue with a Closes #N keyword in both the commit message and the pull-request body. None of them edits CHANGELOG.md.

Only the last one adds public surface: an optional as_of_dates.id_column config key. Absent, the rendered SQL is byte-identical to today's — that is a test, not an aspiration.

[x] Phase 1 — PR A: quote bare identifiers in the synth projection (#13)

_build_synth_cte interpolates every projected name bare, so a target column whose name is not a plain identifier produces invalid SQL. It is invisible while every column is a bare identifier, and it hard-blocks the documented identity-passthrough shape the moment a target's columns are featurizer's own generated names.

The issue's suggested fix does not work as written. It proposes routing the projection through pg_identifier "like every other column reference". pg_identifier is not idempotent — it unconditionally wraps in quotes (abstractions.py:54-60) — and generated feature names are already quoted, which the comment at planner.py:1780 states outright: wrapping again "yields an empty delimited identifier". A blanket application breaks every aggregate and transform column. The fix must discriminate.

1. Add a narrow helper rather than changing pg_identifier

  • [x] Add quote_if_bare(name) beside pg_identifier in abstractions.py: return the name unchanged when it is already a delimited identifier (starts and ends with "), otherwise return pg_identifier(name)
  • [x] Do not make pg_identifier itself idempotent — it is called at feature-construction time in eight places and a silent behaviour change there would reach the ADR-0007 naming contract
  • [x] Do not quote at Variable construction time — variable names flow into the manifest, the one-hot naming contract and the sharding metadata; that is a 2.0-shaped change, not a bug fix

2. Apply it at the projection site only

  • [x] planner.py:1841-1848: build id_columns and feature_names through quote_if_bare
  • [x] Verify the emitted output name is unchanged for bare identifiers: select patients."age" and select patients.age both yield a column named age, so no existing matrix moves
  • [x] Check _synth_columns stays consistent. Line 1852 records set(feature_names) and line 1912 reads it back; whatever is recorded must keep matching what the transform CTE and the sharding metadata expect. Record the output names, not the quoted projection expressions, if those differ

3. Testing Strategy

The regression needs a target entity whose declared variables are not bare identifiers — the exact shape that fails today. Rendering is DB-free, so the primary test costs nothing; the integration tier proves PostgreSQL actually accepts the result.

  • [x] tests/test_synth_quoting.py: a config whose target declares a variable named MEAN(x.y|interval=P30D) renders without a syntax error — this fails on current master
  • [x] Assert a bare-identifier config renders a projection whose output column names are unchanged against a captured baseline
  • [x] just db-up && just test-integration — PostgreSQL parses the generated SQL for both shapes
  • [x] just test-fast · just typecheck · just fmt-check

[x] Phase 3 — PR C: warn that temporal: is inert in the aggregation orientation (#9)

temporal_mode is read at exactly one line — planner.py:1378, inside _build_direct — and the aggregation path never reads it. A temporal: block on a relationship traversed in the aggregation direction is discarded, and validation returns is_valid=True with zero warnings.

This is not a leakage bug. The aggregation path applies causal_predicate unconditionally (planner.py:1526-1530), so the child stream is bounded by as_of_date either way. What is lost is grace — which relaxes the bound — so the effect is a config stricter than the author asked for, not looser. Warning is therefore sufficient and additive; honouring the block would move results for every config that carries an inert one.

1. Warn, and name the working orientation

  • [] Validation emits a warning when a relationship carries a temporal: block and is traversed in the aggregation direction
  • [] The message must name the fix, not just the fault: declare the lookup/dimension table as parent and the timestamped entity as child
  • [] Say that the child stream is already bounded by as_of_date, so the author knows nothing leaked

2. Fix the example that ships the trap

  • [] examples/02-temporal-joins/config.yaml declares mode: as_of, grace: P7D and child_timestamp: plan_date, and renders none of it — verified: zero _asof_for_, no P7D in 242,919 characters of SQL. Its comment promises "matching plans up to 7 days in the future", which does not happen
  • [] Either re-orient the relationship so the as-of join actually renders, or drop the temporal: block and rename the example. An example that emits the new warning is not acceptable — it is the tutorial for this exact feature
  • [] If re-oriented: the notebook under examples/02-temporal-joins/ has committed outputs that the docs site renders from, and site/gen.py never executes them. Re-execute against a live database and commit the new outputs, or the published tutorial contradicts the config

[x] Phase 5 — PR E: pair-table cohorts (#10)

The engine renders from as_of_dates aod cross join lateral (…), so every target row is emitted under every as-of date. Where a cohort pairs each date with its own entity set, all but the diagonal is computed and discarded.

The issue's proposed interface cannot work. It asks featurizer to join on entity_id "if the supplied as_of_dates relation has that column". Rendering is DB-free — Featurizer(cfg).query takes no connection, verified by rendering 242,919 characters of SQL for example 02 with no database available — so the renderer cannot inspect the caller's table. The pairing must be declared.

1. Measure the waste first, with a harness case that can see it

  • [] Add a multi-date case to benchmarks/final_matrix.py. It inserts one as-of date today (lines 174-180); the new case takes N and records rows computed against rows on the diagonal
  • [] Run it on the existing live datasets and record the baseline — this is the "before" number, and the reason #10 went unseen for the project's whole history
  • [] Keep the single-date case exactly as it is: every published figure from ADR-0009 onward was measured with it, and changing it would break comparability with the v1.0.0 revalidation

2. Declare the pairing in the config

  • [] New optional top-level block: as_of_dates: {id_column: <name>}
  • [] Absent → today's behaviour exactly. Not "equivalent", not "near-identical": the rendered SQL must be byte-identical, and that is a test
  • [] Add the key to Phase 2's known-top-level-key set
  • [] Validation can check the key's shape (non-empty string) but cannot check the caller's table has the column — no connection at validate time. A wrong name surfaces as a PostgreSQL error at execute time; say so in the docs

3. Push the predicate into the target's base read

  • [] Add a cohort_predicate beside causal_predicate in boundary.py, same aod-correlated shape and prefix convention
  • [] Apply it in _build_synth_cte, on the target's from {target.table} — not as a filter on the lateral's output. aod is in scope inside every CTE (that is how causal_predicate already works), and a post-filter would return the right rows while still computing the discarded ones, which is the entire cost being removed
  • [] Confirm the aggregation CTEs narrow as a consequence. If they still compute over the full entity set, say so plainly in the pull request and record the real speedup rather than the hoped-for one

4. Document the pattern generically

  • [] New page src/content/docs/concepts/paired-cohorts.md: when each as-of date has its own entity set — an event that happens on a date, a scoring run over that day's arrivals — the dense product computes a matrix the caller throws away, and id_column expresses the diagonal instead
  • [] Contrast it with the default, which is correct and wanted for the standard shape: every entity in the cohort scored at every as-of date, which is what temporal cross-validation means
  • [] Written as a general cohort-shape concept. No consumer, domain or dataset is named
  • [] Add it to the sidebar and cross-link from the configuration reference

Questionables

[asked] #9 warns rather than honouring the block

Chosen: warn only. Additive, nothing on ADR-0015's freeze list moves, and no existing config changes behaviour. Supported by the verification: the aggregation path is already bounded by causal_predicate, so the missing piece is grace, which relaxes the bound — the current behaviour is stricter than declared, not looser. Honouring the block would silently loosen point-in-time bounds for anyone carrying an inert grace.

[asked] Unknown keys are an error, not a warning

Chosen: error, matching Entity(**e)'s TypeError. Chosen over warning despite the consumer blast radius being raised twice: a config that runs today and carries a stray key stops validating, and triage-pg would meet that on a pin bump rather than at authoring time. Phase 2 task 3 exists because of this decision — the consumer's configs are checked before the merge, and a failure there is a finding to act on, not a result to paper over.

[asked] #10 is in scope, declared in the config

Chosen: include it, with as_of_dates: {id_column: …}. Declarative, visible to validate, travels with the config, and additive under the freeze. Explicitly required: when the block is absent the behaviour is exactly today's, enforced by a byte-identical SQL test rather than by assertion.

[asked] #11 gets a cross-reference, not the view

Chosen: the guard is already correct, so no code. Verified against the reporter's own measurements — 979 vs ~1,018 columns, 11,383 vs 11,176 bytes, conservative in both directions. The documentation cross-reference is kept because it costs six lines and closes the half that actually cost time; the shard-joining view is dropped. If the intent was to drop #11 entirely, the cross-reference is the only thing to remove from Phase 4.

[unresolved] Whether the cohort predicate actually narrows the aggregation CTEs

Assumption in force: filtering the target in its base read propagates, because the aggregation CTEs join to the target downstream. But they aggregate the child stream grouped by the child key, and that grouping may not narrow just because the target did — in which case the measured speedup is much smaller than the row-ratio suggests. Phase at risk: 5. Phase 5 task 3 makes this checkable rather than assumed, and the instruction there is to report the real number. If the aggregations do not narrow, the honest outcome is a correct feature with a modest speedup, and the deeper push-down becomes its own plan.

At one date the dense product is exactly the wanted rows. The correctness tier does use more — 2 dates in test_tui_adapters.py:86, 3 in _realistic.py:9 — but at row counts where a 3:1 product is invisible. #11 is the mirror: the ceiling was found and guarded during v1.0 hardening, but the guard only protects the table featurizer writes, and the reporter wrote their own.

The general lesson, worth carrying past this plan: the harness measures one cohort shape, written by one writer. Both gaps sat in the space that shape does not cover, and no amount of additional testing of that shape would have found either.

Freeze posture

ADR-0015 froze the config schema, Featurizer methods, output naming, imputation and the bridge contract. Every phase here is additive against that list:

  • Phase 1 changes rendered SQL only; output column names are provably unchanged (the name-stability snapshot is a validation step).
  • Phase 2 tightens validation. This is the one place to be honest: rejecting a key that was previously accepted is a config-schema change in effect, even though no key's meaning moved. It was chosen deliberately with the consumer risk on the table.
  • Phase 3 adds a warning; is_valid is unaffected.
  • Phase 4 is documentation.
  • Phase 5 adds an optional key that is inert when absent.

Risks worth naming

  • Phase 2 breaks a consumer config. Not hypothetical — that is the point of task 3. Finding it before the merge turns a pin-bump incident into a pull-request comment.
  • Phase 3's notebook. If example 02 is re-oriented, its committed outputs must be re-executed against a live database. site/gen.py renders committed outputs and never executes them, so a stale notebook would publish a tutorial that contradicts its own config — and CI would not notice.
  • Phase 5's speedup may disappoint. See the unresolved questionable. The correctness gate (equality with the dense oracle) matters more than the performance one, and a faster wrong matrix is the failure mode to guard against.
  • No new dependency in any phase. Nothing to uv add, no lockfile churn, so none of these touches rule 2's all-consumer list.
