Purpose

Give every categorical aggregation that reads a value as a category one rule for NULL: a NULL is a state. A primitive must give the same value on a series with NULLs as on the same series with each NULL replaced by a category that appears nowhere else. Close #86 under that rule, including the ngram_3_freq partial trigram folded into it. Ship it in a 1.x minor (1.5.0) under a new ADR-0020 that names every primitive and case whose values move.

Problem

The sequence primitives build (prev, curr) pairs with LAG(x). LAG returns NULL in two different situations: the row has no previous row (it is the first in its window), or the previous row's value is NULL. Five transition primitives and the two n-grams filter prev IS NOT NULL (or lag_1 IS NOT NULL) to drop the first row. That filter also drops every step out of a NULL state. rework_count compares with prev = curr, so a NULL never repeats. ngram_3_freq checks lag_1 but not lag_2, so it counts the second row of every series as a trigram, NULLs or not.

Measured on PostgreSQL 16 on 2026-11-04, these values are wrong under both candidate rules, NULL as a state and NULL as missing data:

sequenceprimitivetodayNULL is a stateNULL is missing
a, NULL, btransitions kepta→NULLa→NULL, NULL→ba→b
a, NULL, NULL, arework_count011
a, NULL, NULL, astate_volatility120
a, bngram_3_freq1NULL (no trigram)NULL

The same engine already treats NULL as a state elsewhere. entropy, hhi and kl_drift group by the value, so NULL is a category. longest_streak and time_in_current_state compare with IS DISTINCT FROM. recurrence_interval partitions by the value. The inconsistent primitives disagree with these on the same rows.

Correction to the issue thread: the registry dict featurizer.primitives.aggregations.DEFAULT_AGGREGATIONS holds every primitive. The selection an omitted aggregations: key applies is featurizer/featurizer.py:38, ten basic aggregations with no sequence primitive in it. A consumer computes the affected primitives only by naming them, and triage-pg's example configs name none (checked 2026-11-04).

Solution

Tell the two meanings apart with a row number from the same window as the LAG. rn = 1 means "no previous row". rn > 1 with prev NULL means "the previous state is NULL". Replace each prev IS NOT NULL filter with rn > 1 (rn >= n for an n-gram), and each prev = curr with prev IS NOT DISTINCT FROM curr. Both paths change together: the set-based pre-pass and the correlated fallback. A shared window means one sort, the pattern longest_streak already uses (ADR-0018). The row number is computed after the as-of cut, inside the same SELECT, so it numbers only rows the feature may read.

The order of work puts the decision first. ADR-0020 is drafted as Proposed before any engine change (Phase 1). Two sweeps then show today's values failing the rule, landed as strict xfails that name #86 (Phase 2). The engine change turns them green (Phase 3), the live databases measure what moves (Phase 4), and the ADR is completed with those numbers and signed before the PR merges (Phase 5).

Definition of Done

Every categorical aggregation in the registry, except the three SQL aggregates count, nunique and mode, gives the same value on a series with NULLs as on the same series with each NULL replaced by an unused category. That holds on the set-based path and on the correlated fallback. The 11 sequence primitives match a Python reference on hand-built sequences, and ngram_3_freq no longer counts an incomplete trigram. ADR-0020 is Accepted and names every value that moved. The PR that closes #86 is merged.

The evidence. The sentinel sweep covers 17 aggregations (20 categorical in the registry on 2026-11-04, minus the 3 SQL aggregates). The reference sweep covers 11 primitives × 2 paths. Strict xfails go from the Phase 2 count (expected 9 primitives) to 0. Hand examples: rework_count on a,NULL,NULL,a goes 0 → 1, state_volatility 1 → 2, and ngram_3_freq on a,b 1 → NULL, from tests/test_sequence_reference.py and the sweep. Questionables

[asked] Plan first, or settle the decision and go straight to an ADR?

The maintainer chose a full plan (2026-11-04), so the decision, the code and the triage-pg check sit in one place.

[asked] Q5. Which NULL rule: state, missing, or state plus an opt-in skip?

NULL is a state. It matches the six primitives that are already coherent, and moves only values that are wrong under both rules, plus the all-NULL dwell.

[asked] Q6. Version path: minor under ADR-0020, opt-in then flip in 2.0, or 2.0 only?

Minor (1.5.0) under ADR-0020, following ADR-0016 and ADR-0018.

[asked] Q7. The ngram_3_freq partial trigram: new issue, fold into #86, or a later PR?

Folded into #86. The issue body was amended on 2026-11-04 with the measurement, and it is fixed by the same rn >= n marker.

[asked] Q8. Consumer impact: live databases plus triage-pg, or triage-pg configs only?

Live databases plus triage-pg (Phase 4).

[decided] count, nunique and mode keep SQL NULL semantics

Their definitions come from SQL (count(x), count(distinct x), mode() within group ignore NULL inputs). Changing them is a semantic change outside #86. The sweep names them, and drops a name if its values turn out equal under the sentinel.

[decided] The marker is a row number from the LAG's own window

Not a LAG over a sentinel value, which could collide with real data, and not a second window, which would mean a second sort (ADR-0018's longest_streak lesson). One WINDOW w carries both columns.

[decided] Two oracles, not one

The sentinel sweep covers the whole categorical registry cheaply, but it cannot see the partial trigram: the trigram exists with and without the sentinel. The Python reference sees it, and checks the 11 sequence primitives against the rule directly instead of against themselves.

[decided] Sweep timestamps at midnight only

That keeps #86 separate from the timestamp-bound mismatch in Notes. The tied and NULL cases do not need a time of day.

[decided] longest_streak and recurrence_interval are left alone unless measured

Out of scope, worth its own issue: the timestamp bound. On a timestamp temporal index, the whole-history bound is ts <= aod.as_of_date, which casts the date to midnight. The interval window is daterange(…, aod.as_of_date::date, '[]') @> ts::date, which takes the whole as-of day. Verified 2026-11-04 on PostgreSQL 16: a row at 2024-06-01 12:00 is outside the whole history and inside the P30D window for as-of 2024-06-01. If the as-of date means its own midnight, the window reads up to a day ahead, which is a point-in-time question. The future-row sweep uses date columns and cannot see it. It is not filed, and this plan's sweeps avoid it by using midnight timestamps.
