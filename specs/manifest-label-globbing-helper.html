Purpose

Add Featurizer.columns_matching() and Featurizer.manifest_matching() so callers can select feature columns by globbing the manifest's full, untruncated label, plus glob_to_like() for anyone writing the equivalent query against the persisted manifest table by hand.

This is the additive resolution of a request that was twice declined as a truncation change. It is legal under the ADR-0015 freeze because it adds surface rather than altering any frozen shape, and it ships as 1.1.0 (a new public method is a minor, not a patch).

Scope was cut after research (2026-08-15, see Amendments). An earlier draft also emitted a PostgreSQL function from to_tables. Investigating the only real consumer showed it has no SQL surface to serve, so that phase was removed along with its ADR, its parity test, and its CREATE FUNCTION privilege hazard. What remains is stdlib-only, database-free, and adds nothing to any persisted shape.

Problem

PostgreSQL caps identifiers at 63 bytes. Featurizer hash-truncates longer feature names keeping the head — so a deep composition erases the innermost, most informative fragment. A glob written against physical column names then misses those columns.

An earlier draft of this plan called that a silent miss. Investigating the real consumer showed that is not accurate, and the correction narrows the scope usefully. Two paths exist in ~/projects/triage/src/triage/adapters/feature_groups.py, and they behave differently:

pathhow it matcheseffect of truncation
group_by='source_entity' (default) column.find(f"{alias}.") — substring, on the physical name Immune. 0 of 1,217 truncated columns lose their alias; 0 change alias.
definitions={group: [globs]} (explicit) fnmatch.fnmatchcase(column, glob) Loud crash — ValueError, never a silent drop.

The default path is immune structurally, not by luck: head-keeping preserves the leading alias. token, which is exactly what the substring search reads. (Corollary worth recording: tail-preserving truncation would have broken this path for nearly every truncated column — independent confirmation of the rejection in .out-of-scope/.)

So the real failure is a dead end, not data loss. Write the obvious glob for an explicit feature group and it targets a tail fragment:

glob '*frecuencia_cardiaca*'
  matches on label : 672
  matches on column: 198   MISSED: 474

Those 474 columns do not vanish from the run — they abort it:

ValueError: feature column 'ABS(patients.MAX(measurements.ABS(measurements.frecuen~1c0ca6e8'
  matches no feature_groups.definitions glob; every column must belong to exactly one
  group (add a glob or widen one).

The advice in that message is unactionable: you cannot write a glob for a hash you cannot predict. Today the only way out is to already know about the manifest and pre-compute the column list by hand — which is this helper, done manually. That is the problem worth solving.

Two secondary cases round it out. Ad-hoc analysis ([c for c in df.columns if 'frecuencia' in c]) is genuinely silent — 198 instead of 672, no signal. And 887 columns already share their visible text with another column before truncation erases anything, so physical names were never a reliable parse surface.

definition is not a usable fallback — the obvious objection, tested and rejected. Of the 1,217 truncated columns, 234 have a definition that itself embeds a ~-truncated parent name: truncation is inherited one level up, not escaped. Worse, the definition drops the window — ABS(patients.MAX(…|interval=P1W)) and its P2W and P1M siblings share a byte-identical definition, so windowed variants are indistinguishable by it. label is the only lossless surface, which is why the manifest carries it.

Solution

One glob syntax (fnmatchcase), matched against label, on one surface:

  • columns_matching(pattern) — physical column names in output order. The answer to "what do I put in my definitions glob list / my select".
  • manifest_matching(pattern) — the full ManifestEntry rows, for labels, lineage, intervals and further filtering.
  • glob_to_like(pattern) — exported from featurizer.manifest for anyone hand-writing the equivalent query against the persisted <stem>_manifest table. A function, not an emitted database object: it solves the _-escaping trap without creating anything to install, privilege, or freeze.
  • Zero matches raise a LookupError that names truncation as the likely cause and points at the manifest — turning triage's unactionable "add a glob or widen one" into a message with a way forward. allow_empty=True opts out.

The intended end state, in the terms of the failure above:

# before — obvious glob, unactionable crash 474 columns in
definitions = {"cardiac": ["*frecuencia_cardiaca*"]}

# after — resolve against the manifest first, glob the real column names
definitions = {"cardiac": f.columns_matching("*frecuencia_cardiaca*")}   # 672 columns
The sharpest correctness risk in glob_to_like: _ appears in 2,007 of 2,104 labels (95%) because snake_case is everywhere. In glob, _ is a literal; in SQL LIKE it is a single-character wildcard. A translation that does not escape _ silently over-matches on nearly every realistic pattern. That trap is precisely why the translator is worth exporting rather than leaving each SQL user to rediscover — and why its escaping order is pinned by exact-string tests in Phase 1.

[x] Phase 2: Zero-match diagnostics

A glob that matches nothing must say so loudly and usefully. This phase is small, and after the research it is the part that carries the most value: the failure people actually hit is triage's ValueError telling them to "add a glob or widen one" when no glob can possibly match a hash. Being loud is already solved upstream — being actionable is what is missing.

Message design target. A caller who lands here should learn three things they cannot learn today: that the pattern matched nothing, that truncation is the likely reason a pattern targeting an inner fragment failed, and what to write instead. Name the manifest explicitly — most people hitting this do not know it exists.

1. Suggestion strategy

  • [x] Implement _suggest_for_pattern(pattern, entries, limit=3) by literal-fragment backoff, not string distance: split the pattern on *?[, take the longest literal fragment, and progressively trim it from the right until some label contains it; return those labels.
  • [x] Rationale to capture in a comment: Levenshtein over ~2,000 labels of ~80 chars is ~107 character operations on an error path, and it answers the wrong question — a glob miss is a prefix/fragment problem, not a spelling-distance problem. validation.py:1178 stays as-is for its own short-token use.
  • [x] Raise LookupError naming the pattern, the match count out of the manifest total, up to 3 suggestions, and the allow_empty=True escape hatch.
  • [x] When the manifest contains truncated columns whose label would have matched the pattern, say so explicitly — that is the difference between a dead end and a fix. Target shape: 
    LookupError: pattern '*frecuencia_cardiaca*' matched 0 of 2104 manifest labels.

Questionables

[asked] Pattern syntax — glob, glob + regex, or regex only?

Chose: glob only. Matches the FAQ's own *(inspections.kw_* example and the request's phrasing ("label-globbing"), and translates to SQL LIKE so a single pattern string works on both surfaces. Regex would have split the SQL story (LIKE versus ~) and doubled the test matrix for power that no known consumer has asked for. Regex remains addable later without breaking this.

[asked] Return shape — one method, two methods, or a group-aware mapping?

Chose: two methods. columns_matching → List[str] for the common "which columns do I select" case and manifest_matching → List[ManifestEntry] for labels and lineage. The group-aware mapping was declined as a return shape but is not lost: the emitted SQL function returns feature_group, and to_tables already hands back per-table column lists to intersect. Coupling the Python helper to the sharding partition would have tied a simple filter to _grouped_for_tables internals.

[asked → reversed] SQL side — emitted function, translator plus docs, or Python-only?

Originally chose: emit a PostgreSQL function (over my recommendation of a translator plus a documented recipe). Reversed 2026-08-15 on evidence, at the user's direction, after they asked why two surfaces were needed — the right question. The only real consumer, triage/adapters/feature_groups.py, is explicitly pure Python, no DB by its own docstring, so the emitted function had no known consumer. It would have cost a database object per run, a CREATE FUNCTION privilege requirement, a second implementation of the translation contract, a parity test to hold the two together, and new surface for 2.0 to freeze — all speculative. Settled: translator plus docs. glob_to_like still solves the _-escaping trap for anyone writing SQL by hand. Revisit if a SQL consumer actually appears.

[asked] Zero matches — raise, warn, or return empty?

Chose: raise by default, allow_empty=True to opt out. A silently-empty glob is indistinguishable from a feature that does not exist, which is the exact failure this helper is built to end; returning [] would have rebuilt the trap inside the fix. Warning was rejected because notebook and pipeline logs go unread.

[obsolete] emit_helpers defaults to False, not True

Moot as of the 2026-08-15 revision — there is no emit_helpers flag, because there is no emitted function. Retained as a record of the reasoning in case the SQL surface is ever revived: to_tables requires only CREATE TABLE today, so defaulting a function emitter on would break every caller whose role lacks CREATE FUNCTION — a breaking change inside a minor, which ADR-0015 forbids. Any future revival must ship opt-in.

[decided] Ships as 1.1.0, not 1.0.2

ADR-0015 freezes the Featurizer public surface and permits additive change in minors. Two new public methods and a new to_tables keyword are additive, so semver makes this a minor. Shipping it as a patch would misrepresent the surface change to a consumer pinning by tag.

[decided] Literal-fragment backoff for suggestions, not Levenshtein

validation.py already has _suggest_similar, so reuse looks obvious — but it is the wrong tool twice over. It is O(n·m²) over ~2,000 labels of ~80 characters on an error path, and a glob miss is a fragment problem rather than a spelling problem: *(inspections.kw_rodnet* should suggest by backing off to (inspections.kw_, which distance ranking would not surface cleanly. validation.py is left untouched for its own short-token use.

[decided] fnmatchcase, not fnmatch

fnmatch.fnmatch applies os.path.normcase, making it case-insensitive on Windows. Feature labels are case-bearing by construction — operators uppercase, aliases and columns lowercase — so platform-dependent matching would be a real correctness bug on the 3.10–3.13 matrix. Case-insensitive matching can be added later as an explicit flag.

[unresolved, downgraded] fnmatch character classes versus one-hot values containing [

Assumption in force: literal [ in patterns is rare enough to document rather than engineer around. Measured on the sample config, no label contains [, ], *, ?, % or \ — but that config has no one-hot columns, and ADR-0007 one-hot labels embed user data as <entity>.<col>=<value>. A value like Type[A] makes a literal-[ pattern behave as a character class. Downgraded by the 2026-08-15 revision: with no SQL side there is no parity divergence — the nastiest version of this — only ordinary fnmatch semantics that a user can hit and diagnose in one place. Phase 1 is now the phase at risk, and the failure is visible rather than silent. Mitigation if it bites: a literal=True mode or glob.escape handling. Still worth one test against a config that actually has one-hot columns.

Notes

Why this plan exists at all

Twice, a consumer met a column named …kw_rod~978dcf98 and proposed reshaping the truncation to keep the readable tail. Twice it was declined on reasoning. On 2026-08-15 it was finally measured, and the intuition turned out to be backwards:

schemevariable lostoperator lostambiguousworst group
head-keeping (today)19708878
tail-keeping (proposed)01171102778
both-ends (steelman)003116

Tail-keeping is a regression. Both-ends dominates but still leaves 311 ambiguous columns, so it cannot retire the manifest — while renaming 57.8% of columns and invalidating every downstream cache. The conclusion recorded in .out-of-scope/tail-preserving-truncation.md is that 63 bytes cannot hold a compositional name and every fixed-window shape merely picks which half to blind you to. This plan is what to build instead.

How the case for this changed under scrutiny

The first draft justified the helper as preventing silent feature loss. Challenged on whether that was real, the honest answer turned out to be no — not for the production consumer. triage's default grouping path is structurally immune, and its explicit path crashes loudly rather than dropping anything. The argument had to be rebuilt on what is actually true, and it is narrower but sturdier:

  1. The dead end (primary). An explicit feature_groups.definitions glob targeting an inner fragment aborts the run on 474 columns with advice — "add a glob or widen one" — that cannot be followed, because no glob matches an unpredictable hash. There is no documented way out today.
  2. Ad-hoc undercount (genuinely silent). [c for c in df.columns if 'frecuencia' in c] returns 198 of 672 with no signal. Not production, but where most exploratory work happens.
  3. 887 already-ambiguous columns. Columns sharing visible text with another column, today, before truncation erases anything. No truncation reshape touches them; only globbing the label does.

What did not survive: the claim that features silently vanish from triage runs. If that had been the justification, this plan would have been solving a problem that does not exist.

Dependencies

None. fnmatch is stdlib and nothing else is needed. No uv add, no new extra, no change to the dependency groups, no database. This is deliberate — the helper must work in the base install, since the whole point is that every consumer reaching for a physical name should reach for this instead.

Risks, in the order they are likely to bite

  1. Escaping-order bug in glob_to_like. Highest probability, highest blast radius: it fails silently and over-broadly, returning too many columns rather than erroring. Mitigated by exact-string assertions in Phase 1, not by review. Note the blast radius shrank when the SQL phase was cut: the translator is now advisory, so a bug affects only hand-written queries, not anything the library itself executes.
  2. An unhelpful zero-match message. Now the plan's main deliverable rather than a nicety. If the LookupError does not name truncation and the manifest, the user is back in the same dead end with a different error class — strictly worse, because they now have two confusing messages instead of one.
  3. Bracketed one-hot values. See the unresolved questionable. Low probability and, without a SQL side, a visible failure rather than a silent divergence.

Deliberately out of scope

  • Changing the truncation shape — rejected with measurement; see .out-of-scope/. Any temptation to "also fix the names while we're here" should be refused, and tests/test_truncation_shapes.py will fail if it is not.
  • Case-insensitive matching — addable as an explicit flag; not defaulted, because labels are case-bearing.
  • A CLI subcommand — featurizer list-primitives has a discovery role, but globbing needs a live config and a plan; the Python surface is the right home.
  • An emitted SQL function — evaluated, chosen, then cut on evidence. See the Questionables entry and the 2026-08-15 amendment.

Matching description / definition — out of scope, but concretely

Deferred, not dismissed. Both fields already exist on every entry, so this is a one-line filter away once manifest_matching lands — the question is only whether the helper should take a field= argument. Real values from the sample config, so the shape of the idea is on the record:

description: "7-period Holt-Winters level (smoothed average), applied to care_plans.ABS(care_plans.plan_score)"
description: "Cumulative sum over time, applied to care_plans.ABS(care_plans.plan_score)"
definition:  ' abs("COUNT(consultations.medical_consultation|interval=P2W)") '
  • Globbing description buys semantic selection without knowing operator spellings. *7-period* catches EMA_7, HOLT_WINTERS_LEVEL_7, ROLLING_MEAN_7 and ROLLING_STD_7 in one pattern; *moving average* catches the smoothers but not the trend components. That is a genuinely useful feature-group definition — "all short-window smoothers" — that no label glob expresses cleanly.
  • Globbing definition buys SQL-level selection — every column whose expression calls abs(, or every column whose SQL touches one suspect source column. Mostly an auditing and debugging tool: "what does this bad column feed?"
  • Caveat that keeps it out of v1: both fields are lossy in ways label is not. 234 definitions embed a ~-truncated parent name, and definitions drop the interval entirely, so windowed siblings are indistinguishable. A field= argument would therefore need to document per-field reliability — real design work, not a parameter.

Sequencing note for the build

Phases 1 and 2 are the feature; Phase 3 is documentation and the version bump. Nothing here carries compatibility risk, so there is no fallback seam to plan for — the change is additive end to end. If time runs short, Phase 1 alone is coherent and shippable, but it should not ship without Phase 2: the helper's value over a one-line list comprehension is the error message.

Amendments

2026-08-15T21:33 — SQL phase cut; problem statement corrected against the real consumer

What changed. Phase 3 (emitted PostgreSQL function, emit_helpers flag, Python↔SQL parity test) and Phase 4's ADR-0016 were removed; the plan went from four phases to three, and from two new files plus an ADR to one new test file. The Problem section was rewritten around measurements rather than assumption.

Why. The user asked two questions the first draft could not answer: is this a real problem — do we actually miss columns? and why do we need two surfaces? Investigating the real consumer (triage/src/triage/adapters/feature_groups.py) produced three findings that changed the plan:

  • triage's default group_by='source_entity' path is immune to truncation — 0 of 1,217 truncated columns lose or change their alias, because head-keeping preserves the leading alias. token the substring search reads.
  • triage's explicit-glob path raises loudly; it never silently drops features. The first draft's "silent miss" framing was wrong for the production consumer. The real failure is an unactionable crash ("add a glob or widen one" — impossible against a hash), plus genuinely silent undercounting in ad-hoc notebook filtering.
  • That module is pure Python, no DB by its own docstring, so the emitted SQL function had no known consumer — speculative surface carrying a CREATE FUNCTION privilege hazard, a duplicated translation contract, and a parity test to hold the two implementations together.

Also tested and recorded: definition is not a usable fallback for label — 234 truncated columns have definitions that themselves embed a ~-truncated parent name, and definitions drop the interval, making windowed siblings indistinguishable.

Net effect. Roughly half the plan removed; the remainder is stdlib-only, database-free, and additive end to end.
